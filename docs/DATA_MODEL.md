## §1 Three findings that shape everything below

Found while reading the seed against `CONTENT_MODEL.md` §3b. Each is stated first because
each changes a schema decision.

### F1 — The harm case §3b step 4 prevents is live in the seed

`PSA (Prostate Specific Antigen)` is a member of `general-checkup` at **Silver**. Silver
unions into Gold, and Silver unions into Platinum (§3b step 2). So a `Visitor` selecting
Gold, or Platinum — Female, on the General Checkup page receives a prostate marker unless
the eligibility filter removes it. Verified:

```
PSA membership rows in the seed:
  general-checkup · Silver           · "PSA Total (male>45only)"
  general-checkup · Platinum — Male  · "PSA(total & Free)for male>45 year only"
```

This is not hypothetical and it is not a display preference. §3b names it a harm vector of
the same rank as the Children constraint.

### F2 — The data that filter reads does not exist

§3b step 4 reads `eligibility.audience` with values `all`, `male`, `female`, and shows
`note_ar` / `note_en` where the selection is `none`. **No such field exists on any of the
72 `LabTest` records.** The restriction survives only inside a free-text `source_name`:
`"PSA Total (male>45only)"`. A string a human wrote in 2018.

The filter is specified and unimplementable against current data. The schema therefore
**fails closed** — see §5.

### F3 — All 72 `LabTest` records have no Arabic name

```
LabTests missing name_ar: 72 of 72
LabTests missing name_en:  0
Programmes missing name_ar: 0 of 9
```

`I18N_MODEL.md` §8 requires every Visitor-facing string in both locales and makes a
missing one a failure rather than a fallback. Seventy-two Arabic clinical names do not
exist. Producing them is Opus-class work by the model rule — *a mistranslated `LabTest`
name on a laboratory site is a harm vector and it is invisible to a reviewer who does not
read clinical Arabic* — and each one then requires the lab's sign-off under the clinical
gate. This work is unscheduled and unpriced.

**Resolved.** F2 and F3 were closed by the laboratory's written clinical sign-off of
6 September 2026 and transcribed by M8 (`20260906110552_m8_signed_catalogue.sql`): 71
`LabTest` rows each carry an Arabic name, all 124 memberships carry an explicit
eligibility value (94 `all`, 16 `female`, 14 `male`, 0 `unreviewed`), and no `qa_flag` is
set. F1's harm case is prevented by §7's eligibility step and the explicit values.

## §2 Naming

**Tables and columns are quoted PascalCase**, exactly matching the entity names in
`CONTENT_MODEL.md` §3a: `"Programme"`, `"LabTest"`, `"ProgrammeLabTest"`.

Postgres folds unquoted identifiers to lower case, so `CREATE TABLE Programme` produces
`programme` — and `GLOSSARY.md` §3 states that lowercase use of a canonical entity name is
a defect, not a style preference. Quoting is therefore not decoration; it is the only way
the schema can carry the vocabulary the project froze.

**The cost, stated rather than discovered later.** Every reference must quote. A query
written as `select * from programme` fails with *relation does not exist*. That is a loud,
immediate failure at the first query rather than a silent divergence between the schema
and the glossary, which is why it is the acceptable cost.

**A CI guard rejects any migration containing an unquoted reference to an entity name.**
The guard runs on `supabase/migrations/**` and fails the build.

Columns follow the same rule where they carry an entity name (`"LabUnit"` as a foreign
key). Ordinary attribute columns are lower snake case: `name_ar`, `display_order`,
`published_at`. Bilingual pairs are always `_ar` and `_en`, in that order, Arabic first
(D-10).

## §3 Rules every table obeys

1. **A `uuid` primary key**, generated by the database. No natural key is a primary key —
   the seed's `id` strings (`kidney-profile`, `psa`) become a `slug` column with a unique
   constraint, because a public path segment must be stable and a primary key must be
   free to change.
2. **RLS enabled**, with the two policy shapes in `SECURITY_MODEL.md` §3. No exceptions.
3. **A publication state.** Anonymous `SELECT` sees only published rows. This is the
   mechanism behind `DESIGN_SYSTEM.md` §12 and behind the clinical gate — an unpublished
   row does not leave the database, so no front-end mistake can render it.
4. **No attribution column.** No `created_by`, `updated_by`, `deleted_by` or `owner_id`
   (D-40, `SECURITY_MODEL.md` §5). `created_at` and `updated_at` are permitted; a person
   is not.
5. **`display_order integer not null default 0`** wherever the `Operator` controls
   sequence. Sorting is data, never a hardcoded array.
6. **Bilingual columns are both present or the row is not publishable.** Nullable in
   storage so a draft can exist half-written; a partial constraint blocks publication
   while either is null. Draft is permitted; a published half-translated page is not.

## §5 `EligibilityAudience`, and failing closed

This is the most consequential decision in this document.

`"ProgrammeLabTest"."eligibility_audience"` is `EligibilityAudience not null default
'unreviewed'`.

**It sits on the membership row, not on `"LabTest"`.** The first cut of this document put
it on the test. `CONTENT_MODEL.md` §3a assigns `eligibility` to `ProgrammeLabTest`, and
§3b step 4 reads it *"for each row in the set"* — those rows are membership rows.
`CONTENT_MODEL.md` is document 4 and this file is document 7, so the higher document wins
and this one is amended. Corrected at P01-T03-R-M3 after the builder reported the
divergence rather than reconciling it. The control is unchanged by the move: the default
is still `unreviewed` and the filter still fails closed.

**A row whose eligibility is `unreviewed` never renders on the public site, in any tier,
for any audience selection.** It is visible in the dashboard, editable, and absent from
every public page.

The alternative was to default to `all`, matching §3b's "always renders, no note". That
default would put PSA on a Gold page and on a Platinum — Female page from the first
migration, because `all` is exactly what F1 describes as the harm. **A safe-looking
default is how this class of defect ships.**

So: all 121 membership rows begin `unreviewed`, every one is therefore withheld from the
public site, and each becomes visible only when a human sets its value. The count is 121
rather than 72 because eligibility is a property of a test *within a programme tier*: the
seed carries PSA twice, at Silver and at Platinum — Male, and each membership is judged. That is the same shape as the
clinical gate and it is deliberate — the eligibility of a clinical analysis is a clinical
judgement, and it belongs with the sign-off that governs the name.

`note_ar` and `note_en` are nullable text, shown per §3b step 4 when eligibility is
`male` or `female` and the selection is `none`.

**Consequence, stated plainly:** until eligibility is reviewed, `Programme` detail pages
render no `LabTest` rows. That is correct. A page that lists nothing is recoverable; a
page that shows a prostate marker to a woman is not.

## §7 The cumulation rule is a database function, not application code

`CONTENT_MODEL.md` §3b defines a four-step rule whose steps 1 and 4 are both named harm
vectors. It is implemented **once**, as a SQL function, and every caller uses it.

```
"programmeLabTests"("programme" uuid, tier ProgrammeTierAxis, audience AudienceAxis)
  returns table (every "LabTest" column, note_ar, note_en)
```

As delivered at M4a the function returns a table rather than `setof "LabTest"`, because
the note shown for a restricted row belongs to the membership, not to the `"LabTest"`.

Reasons, in order of weight:

1. **One implementation can be tested; three cannot be kept identical.** A public page, a
   dashboard preview and a future export would each reimplement the union, and the third
   one written under time pressure is where a child's page gains a tumour marker.
2. **It sits below the front-end.** A component that forgets the rule cannot bypass it,
   because there is no unfiltered query to call.
3. **It is verifiable in isolation.** The Children case and the PSA case are each a single
   assertion against the function.

The function implements §3b exactly: Children returns and never unions · Silver, Gold and
Platinum cumulate in that order · Platinum additionally matches `AudienceAxis` · the
eligibility filter applies after the union and never to the Children branch · and rows
whose eligibility is `unreviewed` are excluded unconditionally (§5).

It reaches memberships **through `"ProgrammeTier"`** (§6 row 3): the axes are columns of
the tier, so the union is a join across tier rows of one `"Programme"` rather than a
filter on axis columns repeated per membership.

**The function is `security definer` with a fixed `search_path`**, so it cannot be
subverted by a caller's schema. It reads only published rows.

**Two further functions exist, neither of them a catalogue rule.**
`public."currentNelPrincipal"()` returns the caller's `nel_principal` from live
server-side account state; the `Offer` partner-read policy calls it, so a revoked
`PartnerLab` stops reading on its next request rather than at token expiry (OD-28,
ADR-002). It is `security definer`, `stable`, with a fixed `search_path`, and executable
by `authenticated` only. `public."enforcePublicationMaximum"()` is the trigger function
behind OD-27: it refuses a publish that would exceed a module's `published_maximum`.

## §8 Integrity, expressed as constraints rather than a script

`verify_seed.py` currently proves after the fact that 121 membership rows resolve to 72
unique `LabTest` records. In the schema this stops being a check and becomes impossible to
violate:

| Rule | Mechanism |
|---|---|
| Every membership points at a real `LabTest` | foreign key, `on delete restrict` |
| Every membership points at a real `ProgrammeTier` | foreign key, `on delete cascade` |
| Every tier points at a real `Programme` | foreign key, `on delete cascade` |
| No duplicate membership | unique on (`ProgrammeTier`, `LabTest`) |
| 121 rows in, 72 distinct `LabTest` out | asserted **inside the seed migration**, which aborts on any other figure. M4c's 2018 seed; the signed catalogue is 124 → 71 after M8 |
| One `SiteSettings` row | unique index on a constant expression |
| At most one head office | partial unique index on `is_head_office` where true |
| `valid_until >= valid_from` | check constraint on `"Offer"` |
| A published row is bilingually complete | partial check per bilingual pair, where state is `published` |
| A published `Announcement` is dated and affirmed | two check constraints, where state is `published` |
| No module exceeds its publishing maximum | the `enforcePublicationMaximum` trigger (OD-27) |

The 121→72 assertion lives in the migration rather than in a spec, because a migration
that silently loads 120 rows is worse than one that fails.

## §9 Indexes

Written where a query needs them and nowhere else. An index on a nine-row table is
decoration.

- `slug` on `"Programme"`, `"LabTest"`, `"LabUnit"` — unique, and the lookup path for
  every detail page.
- `("Programme", tier_axis, audience_axis)` on `"ProgrammeTier"` — the function in §7
  selects tier rows on exactly this, then joins to `"ProgrammeLabTest"` on the tier key,
  which the unique constraint in §8 already indexes.
- Publication state on every published table, because RLS filters on it for every
  anonymous read.
- Bilingual search across `name_ar`, `name_en` and `aliases` — **not a database index.**
  Search is a build-time artefact (OD-02, `CONTENT_MODEL.md` §3f), delivered at P04, and
  cross-script matching is decided by D-50. No database search index exists.

**M4c and M8 are the only migrations that change catalogue data**, and each asserts its
own figures inside the transaction: 121 and 72 for the 2018 seed, 124 and 71 for the
signed catalogue.

**RLS is enabled in the same statement block that creates each table. Policies land in
M4. These are two different things and conflating them is a security defect.**

The first cut of this section said policies land in M4 "so that no table exists
unprotected between migrations", which was backwards: if M2 creates tables and M4 grants
them policies, those tables sit for two migrations with no policy at all. Corrected at
P01-T03-R-M1 after `supabase/config.toml` surfaced the question.

What actually makes the gap safe is that **a table with RLS enabled and no policy denies
every request.** Postgres has no implicit allow. So:

- `alter table ... enable row level security` is in the same `create table` block, in M2
  and M3, never deferred.
- Policies land in M4, when the shapes in `SECURITY_MODEL.md` §3 can be written against a
  complete schema.
- Between M2 and M4 the tables exist and are readable by nobody, including a holder of
  the publishable key. That is the intended state, not a gap to be tolerated.

**A table created without RLS in the same migration is a defect regardless of what the
policies do later**, and `supabase/config.toml`'s `auto_expose_new_tables` is why: if that
flag is ever set, a new table is granted to `anon` on creation, and the only thing
standing between a grant and a public read is RLS being on. The justification matters as
much as the conclusion here, because a wrong justification is how someone later moves
`enable row level security` into M4 alongside the policies it appears to belong with.
